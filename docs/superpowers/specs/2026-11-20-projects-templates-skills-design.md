# 项目、模板库和技能库：整体设计

日期：2026-11-20 · 状态：待确认

这份文档定下整件事的范围、已做的决定和分块顺序。每一块在动手前还会有自己的详细设计。

## 为什么

MagicBot 要改成以短剧创作为核心的工具：一个项目就是一部短剧。

现在左侧以团队（部门）为主，团队和具体的工作绑在一起。同一支团队要做第二部剧，只能在同一批机器人里接着做，两部剧的记忆会混在一起。团队的设定也没法提前准备好、重复使用。

## 目标

1. 左侧以项目为主：全局主 bot 加项目列表，每个项目展开是它的团队。
2. 可以提前准备 bot 模板和团队模板，比如“都市短剧创作团队”“古风创作团队”。
3. 建项目时选一个团队模板，程序在项目根目录下建好项目文件夹，并生成一支新团队。
4. 多个项目可以用同一个团队模板，但团队数据和记忆互相隔离。
5. 项目的团队和记忆放在项目文件夹的 `.magic-team` 目录下。
6. 可以手动建项目，也可以跟主 bot 对话，由它选好团队后建项目。
7. 有一个全局的技能库和 MCP 入口。用户自己上传技能包，机器人按需要自动使用。

## 这一版不做

- 每个项目一套独立的数据目录或独立的服务进程。
- 把聊天记录放进项目文件夹。
- 修改 bot 模板后，自动改动包含它的团队模板。
- 修改模板后，自动改动已经建好的项目。
- 上传 MCP 安装包。MCP 是连接外部服务，不是安装文件。
- 项目的阶段和进度看板。
- 把现有的部门自动转成项目。
- 删除项目。这一版只有归档，文件夹由用户自己删除。
- 在另一台电脑上打开一个已有的项目文件夹。
- 给项目改名，或者移动项目文件夹。
- 把已有的机器人移入或移出项目。

## 已定的决定

| 问题 | 决定 | 原因 |
|---|---|---|
| 项目数据放哪里 | 所有项目在同一个工作区里；`.magic-team` 放团队设定副本、机器人记忆和机器人学到的技能；聊天记录留在全局数据里 | 多个项目要能同时干活；主 bot 要在所有项目之上 |
| 模板改动后已有项目怎么办 | 建项目时复制一份，之后不受影响；可以手动“从模板更新”或“存回模板” | 正在做的项目不应该中途变样 |
| 项目有没有自己的负责人 | 有。团队模板里指定负责人，项目内分工由它安排；全局主 bot 只管建项目和跨项目的事 | 负责人只需要了解一部剧 |
| 技能更新后已有项目怎么办 | 所有项目共用技能库里的同一份，更新后立刻都用新版 | 平台规则这类知识应该始终用最新的 |
| 主 bot 建项目要不要确认 | 要。先出确认卡片，用户点确认才创建 | 建文件夹不像改设置那样容易撤销 |
| bot 模板和团队模板的关系 | 团队模板里各存一份机器人设定；建团队模板时可以从 bot 模板里挑 | 同一个角色在不同题材的团队里常常要不同的设定 |

## 名词

- **全局主 bot**：现有的 MagicBot，不属于任何项目。
- **项目**：一部短剧。对应一个项目文件夹和一支团队。
- **项目负责人**：项目团队里的领头机器人，由团队模板指定。
- **bot 模板**：一个角色的设定，比如“选书”“剧本编写”“镜头脚本设计”。
- **团队模板**：一个负责人加若干成员的设定。
- **技能库**：全局的技能集合，所有项目共用。
- **项目根目录**：用户在设置里指定的文件夹，新项目都建在它下面。

## 设计

### 1. 整体结构

全局的东西只有一份，所有项目共用：

- 全局主 bot 和收件箱
- 技能库
- MCP 服务，以及它们的密钥和登录
- 模板库
- AI 模型设置
- 项目清单

属于项目的东西每个项目各一份：

- 项目文件夹
- 一支团队：一个负责人加若干成员
- 团队的背景说明和团队记忆
- 每个机器人的记忆和它自己学到的技能
- 项目内的群聊和例行任务

现有的部门原样保留，显示在项目列表下面。

### 2. 技能库和 MCP

**技能库**

- 技能库功能已经存在，默认关闭（开关 `features.skillsLibrary`）。这一块把它默认打开，但不把机器人自己的技能搬进库里。
- 技能存在 `<数据目录>/skills-library/` 下，全局一份。
- 底部“工具”里加“技能库”一项，打开技能库页面。“设置 → 你和你的机器人 → 技能”里的同一块内容保留。
- 加上传技能包：`.zip`、`.skill` 压缩包，或一个带 `SKILL.md` 的文件夹，里面可以有脚本和参考资料，也可以一次带多个技能。原来只能粘贴 `SKILL.md` 的文字。
- 新上传的技能先停用，用户看过内容后再开启。这是现有做法，保留。
- 库里已有同名技能时：内容相同就不动；内容不同要用户点“替换”，替换后也先停用。
- 删除不弹确认，删除后可以“撤销”。删掉的内容移进归档目录，不真正删除。
- 技能可以分配给指定的机器人，也可以设成“所有机器人”。这两种现在的意思是：始终列在这些机器人的技能清单里。

**机器人怎么用技能**

- 机器人平时只看到每个技能的名称和一句说明，任务对得上时才读技能的完整内容。这是现有做法。
- 模板里给每个角色指定它的技能，建项目时自动分配。
- 用户放进库里并启用的技能，对所有机器人开放：不超过 15 个时每个机器人都列出全部；超过时只列和它职责最相关的 15 个，其余的它在任务需要时用 `skills_list` 搜到。
- 机器人自己学到后分享出来的技能不在此列，仍然只给被分配到的机器人。
- 技能和职责的匹配支持中文（按相邻两个字）。

**MCP**

- 底部“工具”里加“MCP 服务器”一项，打开现有的“应用 → MCP 服务器”页面。“应用”入口固定打开应用那一面。
- MCP 服务可以按机器人指定。模板里给每个角色写明它要用的 MCP 服务，建项目时自动设好。
- 没有指定的机器人沿用现有行为。

### 3. 模板库

**存放**

- 模板存在 `<数据目录>/templates/` 下，bot 模板和团队模板各一个子目录，每个模板一个文件夹。
- 沿用现有的模板文件夹格式：`bot.md` 或 `team.md`，加上 `skills/` 和 `avatars/`。读写用现有的代码（`shared/share-folder.ts`、`shared/package-format.ts`）。
- 现有格式故意不带模型选择，也会丢掉它不认识的字段。所以模型、技能库引用和 MCP 服务这三项，写在模板文件夹里另一个文件 `magicbot.json` 中，按角色记录。这样模板仍然能用现有的导入导出功能。

**团队模板的内容**

- 名称，和一段“适合什么题材”的说明。主 bot 靠这段说明挑团队。
- 一个负责人和若干成员。每个角色有：名字、职责、人设、外观、模型、技能、MCP 服务。
- 团队的背景说明。
- 可选的初始记忆。
- 版本号。模板每保存一次，版本号加一；项目记下建项目时用的版本。

**技能的两种带法**

- 引用技能库里的技能：只记名字，所有项目共用同一份。
- 模板自带的技能：随模板复制，成为项目里机器人自己的技能。

建项目时如果引用的技能在技能库里找不到，建项目的窗口里会列出来，其余照常创建。

**页面**

设置里加“模板”页，可以：

- 新建、编辑、删除 bot 模板。
- 新建、编辑、删除团队模板。添加成员时可以从 bot 模板里挑，挑进来的是一份副本。
- 把现有的机器人存成 bot 模板，把现有的部门存成团队模板。这用的是现有的“共享”导出。

### 4. 项目

**项目根目录**

- 在设置的“数据”页里配置。
- 必须是一个绝对路径，不能在程序自己的数据目录里面。
- 没有配置时不能建项目，建项目的窗口会带用户去配置。

**项目清单**

项目清单存在 `<数据目录>/projects.json`，每个项目记录：

- 编号、名称、项目文件夹路径
- 对应的部门名
- 用的团队模板和模板版本
- 负责人是哪个机器人
- 创建时间、归档时间

一个项目对应一个部门，部门名就是项目名。这样项目直接用上部门已有的背景说明、团队记忆和负责人机制。

**建项目的步骤**

1. 用户给出项目名，选一个团队模板。
2. 程序检查项目名能不能当文件夹名，根目录下有没有同名文件夹，以及有没有同名的项目或部门。有任何一项重名就拒绝。
3. 建项目文件夹和里面的 `.magic-team`。
4. 按模板生成一支新团队：新的机器人、新的部门。机器人的工作文件夹都指向项目文件夹。
5. 负责人成为这个部门的负责人。
6. 按模板分配技能、MCP 服务和模型，写入背景说明和初始记忆。
7. 模板里的例行任务建好后是暂停的。这是现有做法。
8. 把项目记进项目清单，写好 `.magic-team` 里的副本。

任何一步失败，就撤销前面已经做的，不留半个项目。

**文件夹结构**

```text
<项目根目录>/
  霸总的替身新娘/              项目文件夹，机器人在这里工作，成果放这里
    .magic-team/
      project.json            项目信息的副本
      team/                   团队设定的副本：人设、背景说明、团队记忆
      bots/
        <角色>/               这个机器人的记忆和它自己学到的技能
```

**哪些以 `.magic-team` 为准，哪些只是副本**

| 内容 | 以哪里为准 | `.magic-team` 里 |
|---|---|---|
| 每个机器人的记忆 | `.magic-team/bots/<角色>/` | 真实数据 |
| 机器人自己学到的技能 | `.magic-team/bots/<角色>/skills/` | 真实数据 |
| 机器人的人设 | 程序数据 | 副本，在 `team/` 下 |
| 团队的背景说明 | 程序数据 | 副本，在 `team/` 下 |
| 团队记忆 | 程序数据 | 副本，在 `team/` 下 |
| 项目信息 | 程序数据里的项目清单 | 副本，`project.json` |
| 聊天记录 | 程序数据 | 不放 |
| 技能库里的技能、MCP 服务、模型设置 | 全局 | 不放，`team/` 里只记名字 |

规则是：机器人自己写的东西真的存在项目文件夹里；会进入其他机器人提示词的东西，以程序数据为准。原因见“安全”一节。

副本在创建时写入，之后每次来源变化时更新。程序不会把副本读回来。

**机器人工作区的位置**

现在每个机器人的工作区在 `<数据目录>/workspaces/<机器人编号>/`。项目里的机器人改为 `<项目文件夹>/.magic-team/bots/<角色>/`。不属于项目的机器人不变。

`<角色>` 是模板里这个角色的标识，在一个项目里不重复。项目建好后，负责人或用户给项目加的机器人也属于这个项目，工作区同样放在 `.magic-team/bots/` 下。

项目文件夹找不到时，比如外接硬盘没接上：

- 项目在左侧显示为“找不到项目文件夹”。
- 这个项目的机器人不运行。
- 程序不会自己去新建这个文件夹。

**项目之间的隔离**

- 项目里的机器人只能看到本项目的同事和全局主 bot，也只能把工作交给他们。
- 不属于项目的机器人看不到项目里的机器人。
- 全局主 bot 只和各项目的负责人联系，不直接指挥项目里的成员。
- 用户自己可以和任何一个机器人对话。

这条规则加在机器人互相联系的那一处判断上（`server/peer-roster.ts`），让“机器人被告知的同事名单”和“实际能联系到谁”保持一致。

**左侧**

- 最上面是全局主 bot 和收件箱。
- 下面是项目列表。每个项目一行，展开后负责人在前，成员在后。
- 列表末尾是“新建项目”。
- 再下面是现有的部门，不变。

**归档**

- 项目菜单里有“归档”。归档后项目从左侧消失，例行任务暂停，机器人不再接新工作。
- 文件夹和数据都不动。
- 可以在设置的“数据”页里恢复。

### 5. 主 bot 建项目

全局主 bot 多两个工具，只有它能用：

- **看团队模板**：列出所有团队模板的名称、适合的题材和成员角色。
- **提议建项目**：给出项目名、选的团队模板和用户的需求。

提议之后，对话里出现一张确认卡片，写明项目名、文件夹路径、团队模板和成员，有“创建”和“取消”两个按钮。用户想改，就直接跟主 bot 说，它重新提议。

用户点“创建”后：

1. 走和手动建项目完全相同的步骤。
2. 主 bot 把用户的需求交给项目负责人。
3. 主 bot 回复里带上项目的入口。

没有合适的团队模板时，主 bot 说明情况并列出现有的模板。它不会自己新建模板。

### 6. 模板同步

都由用户手动发起，都先给用户看改动内容，确认后才执行。

- **从模板更新**：把模板的最新设定应用到一个已有项目。列出哪些角色的人设、模型、技能变了，有没有新增或去掉的角色。机器人的记忆不动。
- **存回模板**：把一个项目当前的团队设定存成模板的新版本，或者另存为新模板。
- **沉淀到技能库**：把项目里机器人学到的一个技能加入技能库。
- **沉淀到模板**：把一条记忆加入模板的初始记忆。

## 安全

- **人设不放在机器人能改的地方。** 现有代码特意把人设放在机器人工作区之外，防止它读了带恶意内容的网页后改掉自己的设定。项目文件夹是机器人的工作文件夹，所以人设、背景说明和团队记忆在 `.magic-team` 里只有副本，程序不读回。
- **新技能先停用。** 技能包可能带脚本，机器人会照着技能内容去做。
- **主 bot 建项目要用户确认。**
- **项目名要检查。** 不能含路径分隔符、`..` 或系统保留名，长度有上限。
- **已知的风险。** 桌面版没有沙盒，机器人在完全访问模式下能改项目文件夹里的任何文件，包括同项目其他机器人的记忆。现在的数据目录也有同样的情况，但记忆放进工作文件夹后，更容易被批量替换或清理这类操作误伤。应对办法是在机器人的提示词里写明：`.magic-team` 里只能动自己的那个文件夹。

## 分块和顺序

每一块做完都能单独用。每一块动手前先写自己的详细设计。

| 顺序 | 块 | 做完后能做什么 | 依赖 |
|---|---|---|---|
| 1 | 技能库和 MCP 入口 | 在“工具”里打开技能库，上传技能包，分配给机器人；机器人按需查找技能；从“工具”里打开 MCP 页面 | 无 |
| 2 | 模板库 | 在设置里管理 bot 模板和团队模板，把现有机器人或部门存成模板 | 第 1 块，模板要引用技能 |
| 3 | 项目 | 配置项目根目录，手动建项目，左侧按项目显示，项目之间隔离，归档 | 第 2 块 |
| 4 | 主 bot 建项目 | 跟主 bot 说需求，它选团队、出确认卡片、建项目并交给负责人 | 第 3 块 |
| 5 | 模板同步 | 从模板更新、存回模板、沉淀到技能库和模板 | 第 3 块 |

第 3 块最大，风险也最高。

## 风险和还没验证的事

1. **技能库的完整程度。** 它默认关闭，我还没有实际打开用过。第 1 块的第一步是打开它，确认现有功能都能用。
2. **搬动机器人工作区。** 记忆的索引、机器人自己的技能、AI 引擎能访问的文件夹，都假定工作区在数据目录下。这是第 3 块的主要风险。
3. **多个负责人。** 每个项目一个负责人，加上全局主 bot。要确认现有的负责人机制能做到“一个部门一个负责人，全局主 bot 在它们之上”。
4. **会跨机器人读数据的工具。** 比如搜索过往对话。要逐个检查，确认它们读不到别的项目。
5. **项目根目录的位置。** 放在外接硬盘上，硬盘没接上时项目不能用。放在网盘同步目录里，记忆文件可能产生冲突副本。

## 怎么验证

按 `docs/verification/README.md` 的规定，每一块都在独立的测试实例上验证，不动用户正在用的数据。

每一块的详细设计里会写明要验证的场景。整体上要确认的是：

- 同一个团队模板建两个项目，一个项目里机器人记住的事，另一个项目的机器人不知道。
- 一个项目的机器人联系不到另一个项目的机器人。
- 两个项目可以同时干活。
