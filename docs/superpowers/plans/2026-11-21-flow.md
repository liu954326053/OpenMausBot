# 团队流程：实现计划（flow 线）

日期：2026-11-21 · 设计：`docs/superpowers/specs/2026-11-21-teams-flow-project-canvas-design.md` 第 4 节

**目标：** 团队里谁是谁的上级由一棵树规定，负责人是根。人在团队地图上拖线来画；服务器把它存在 `team-flows.json`；项目按分身的原机器人换算原团队的流程；机器人只能把工作派给直接下级，同事名单里只列上级和下级。

**做法：** `server/team-flow/` 存流程、在成员变化时改写、回答 `parents(section)` 和 `projectParents(projectId)`。`server/peer-roster.ts` 通过注入的查询知道每个机器人在流程里的位置：名单（`reachablePeers`）只留上级和直接下级；`resolveTeammate` 在受理交接时按"工作只往下、问题可以往上"拒绝，并说出能派给谁。工作开始和交回时不按流程再查，所以已经派出的工作照常交回。团队地图的树画在自己的文件里，`TeamCanvas.tsx` 只换掉非电脑视图里"负责人 → 成员"那一段。

## 这一块定下的细节

### 流程的范围

- 团队：有负责人（没归档、不是主机器人）的部门，项目自己的部门除外。一般区域和没有负责人的部门没有流程，里面的机器人照旧联系。
- 成员：部门里没归档、不是主机器人的机器人。主机器人不在任何流程里。
- 项目：负责人是根，项目里每个没归档的机器人都在项目的流程里。没有负责人的项目没有流程，项目的墙照旧。

### 存放

- `team-flows.json`（0600，原子写）：`{ "version": 1, "teams": { "<部门记忆键>": { "<机器人 id>": "<上级 id>" } } }`。只记有人指定过的线；指向负责人等于没指定，不记；负责人自己没有记录。按记忆键记，所以部门改名不丢流程，删除部门后作废。
- 读的时候按当前成员换算：记下的上级不在团队里了，就沿着它记下的上级往上找，找不到就挂在负责人下面。所以服务器没看到的变化（停机时改了数据）也不会出错。
- 改写：成员被删除、归档或移出团队时，指向它的线改指它原来的上级，它自己的记录去掉；换负责人时去掉新负责人自己的记录；启动时把已经不成立的记录清一遍。都是有变化才写。
- 文件读不出来（不是 JSON、格式不对）：服务器照常启动；每支团队按默认流程回答（全体成员挂在负责人下面），派发规则照常按它生效；不改也不覆盖这个文件，成员变化时也不改写；改线的请求拒绝并说明（从备份恢复 `team-flows.json`）；团队地图显示这句话、不能画线；日志写一行。服务器每 2 秒按路径看一次这个文件，修好后自动用上。
- 部门的记忆键读不出来（`section-contexts.json` 坏了）：同样按默认流程回答，改线拒绝（`serverError.department.readFailed`）。

### 换负责人

新负责人成为根，去掉它自己原来的上级。没指定上级、原来挂在旧负责人下面的成员，现在挂在新负责人下面；新负责人原来的下级仍在它下面；旧负责人如果还在团队里，作为成员挂在新负责人下面；其余的线不变。存储里只需要去掉新负责人自己的记录，其余由"没指定就挂在负责人下面"自然得到。

### 画线的规则

- 给成员指定上级会替换原来的上级。
- 拒绝并说明：会形成回路；负责人当下级；自己当自己的上级；上级不在同一支团队；主机器人、一般区域里的、已归档的、项目里的机器人；团队还没有负责人；流程文件或部门读不出来。
- 去掉一条线：成员回到负责人下面。只有指定过的线能去掉。

### 项目里的流程

`projectParents(projectId)`：负责人以外的每个机器人 → 上级。分身在跟随（有 `source`、没有 `sourceLeft`），而且原机器人在团队流程里：沿团队流程往上找，第一个在本项目里有跟随中分身的原机器人，那个分身就是上级；一直找不到就是负责人。原机器人不在流程里、分身不跟随、项目没有原团队（第 1 块以前建的）或原团队已删除：上级是负责人。项目里不能直接画线，地图上说明要去原团队改。

### 谁能把工作派给谁

- 在流程里的机器人只能联系上级和直接下级，别的都联系不到，包括主机器人、其他团队、一般区域和另一处的机器人。工作、只通知（`reply: "none"`）、往同事的线程里留言：只能给直接下级。提问（`consult: true`）和回答同事在等的问题（`answers`）：上级或直接下级。
- 不在流程里的机器人（主机器人、一般区域、没有负责人的部门）不变。主机器人在项目里仍然只联系负责人。
- 拒绝时说明它能把工作派给谁、能问谁。
- 只在受理时检查。已经受理的工作在开始和交回时不再按流程查：改线之前派出的工作照常做完，结果交回派它的上级。交回本身是现有的交接机制（结果回到派工作的那一轮），不改，只加测试确认。
- 管理权（`canManage`、负责人替人回答问题）不按流程收窄，只有"能不能联系到"按流程。
- 各条路径：
  - `coordinate_bots`（含房间里的交接、`post_to_thread`、跟进已有的线程）：按上面的规则。
  - `post_to_room`：不管。它只往群聊里加一条消息，不开始任何一轮。
  - 群聊里的 @提及：不管。群聊是人建的，成员是人选的；提及只在人发起的一轮里被跟随，次数有上限。
  - `list_threads`、`close_thread`、`wait_until`、实时名单、房间名单、负责人建群聊：都用同一份名单，所以只看到流程里的同事。
  - 另一处（bot link）：流程里的机器人和项目里的一样，看不到也联系不到。

### 提示词

- 有下级的机器人：列出每个下级的名字、职责和说明，并要求按顺序往下派。
- 有上级的机器人：写明上级是谁；做完时先用 `attach_file` 附上自己做出的文件，结果会自己回到上级那里。
- 负责人和普通成员提示词里"能联系任何机器人"的说法，在流程里换成流程的说法。名单放在每轮会变的那一段，规则放在稳定的那一段。

### 团队地图

- 自己的文件：`src/lib/team-flow.ts`（读流程、树的布局）、`src/components/team-flow/`（树、线、圆点、拒绝提示）。`TeamCanvas.tsx` 只把非电脑视图里那一段换成流程树，团队块的大小改由树的布局给出。
- 树按层从左往右排，线用 SVG 画。卡片右侧有圆点，从圆点拖到另一张卡片上就设上级；点一条指定过的线选中它，再按 Delete 或点"去掉这条线"。拒绝时在地图上说明原因。
- 电脑视图不变，不画流程线；一般区域不画。
- 只有主人或管理员能读和改流程；别人看到的地图和现在一样。

### 路由

- `GET /api/team-flows`：每支团队的流程，和文件是否读得出来。
- `PUT /api/team-flows/line`：`{ botId, superiorId }`；`superiorId: null` 去掉这条线。
- `GET /api/team-flows/projects/:id`：一个项目的流程（给项目画布用）。
- 都要主人或管理员。

## 约束

- 只写 `wt/flow` 这个工作树。`server/index.ts` 只加一行（建流程服务、挂路由），另外几处是行内改动：交接种类传给 `resolveTeammate`、流程里的机器人不走另一处、房间名单知道是谁在读。
- 共用文件：`src/locales/*.json` 的新键都在 `teamFlow.` 和 `serverError.teamFlow.` 下，各文件放在一处；`TeamCanvas.tsx` 改动尽量小，`sidebar` 线也在改它。
- 不加依赖。不放宽测试。

## 接口

```ts
// shared/team-flow.ts
export interface TeamFlowWire { section: string; chiefId: string | null; parents: Record<string, string>; placed: string[] }
export interface TeamFlowsWire { readable: boolean; teams: TeamFlowWire[] }
export interface TeamFlowLineInput { botId: string; superiorId: string | null }
export interface ProjectFlowWire { projectId: string; leadId: string | null; parents: Record<string, string> }

// server/team-flow/service.ts
parents(section: string): Record<string, string>;      // 负责人以外的每个成员 → 上级；没有流程时为空
projectParents(projectId: string): Record<string, string>; // 负责人以外的每个项目机器人 → 上级
lineOf(botId: string): { superior: string | null; subordinates: string[] } | null; // 不在流程里为 null
```

## 怎么验证

- 给成员指定第二个上级，替换第一个。
- 会形成回路的线被拒绝，并说明原因。
- 负责人不能放到任何人下面。
- 删除一个成员，它的下级挂到它原来的上级下面。
- 派给不是直接下级的机器人被拒绝，拒绝的话说出能派给谁。
- 派给直接下级照常进行，结果回到上级。
- 同一支团队建的两个项目，改团队流程后都跟着变。
- 第 1 块以前建的项目，每个机器人都在负责人下面。
- 团队地图上画一条线、看到它、去掉它，有截图。

## 已知的不足

- 只能派给直接下级，可能太死（设计"风险"第 5 条）：想问另一条线上的同事，只能经过上级。先按严格的做。
- 改线不收回已经派出的工作。
- 群聊里的 @提及不受流程限制。
