# M1.2: Agent Main Runtime Loop

## Overview

M1.2 implements the **Agent main runtime loop**, the orchestration engine that connects M1.1 (OpenAI-compatible client & streaming) and M1.4 (tool system) into a complete agent reasoning cycle.

**Status**: ✅ Complete  
**Location**: `studio/server/runtime/loop/agent-loop.ts`  
**Branch**: `studio`

---

## Architecture

### Core Responsibility

The AgentLoop manages a conversation turn through the following steps:

1. **Input**: Receive conversation messages
2. **LLM Call**: Stream response from AgentEngineAdapter (M1.1)
3. **Parse**: Extract tokens and tool_calls from streaming response
4. **Tool Execution**: Dispatch tool calls through ToolRegistry (M1.4)
5. **Collect Results**: Gather tool execution outcomes
6. **Loop**: Append results to history and iterate until completion
7. **Stream Output**: Emit events at token granularity to caller

### Data Flow

```
Message History
      ↓
AgentLoop.run() ─→ AgentEngineAdapter.run()
                      ↓
                  OpenAICompatibleClient
                      ↓
                  parseOpenAIStream()
                      ↓
                  Accumulate tokens & tool_calls
                      ↓
                  ToolRegistry.get()
                      ↓
                  ToolDefinition.execute()
                      ↓
                  Format tool results
                      ↓
                  Append to history
                      ↓
                  yield AgentLoopEvent
```

## Key Features

### 1. Streaming Support

- **Token-level emission**: Each token is yielded immediately via AsyncGenerator
- **Tool call streaming**: Incremental assembly of tool arguments from SSE chunks
- **Non-blocking**: Caller can process events as they arrive

### 2. Tool Execution & Permission Management

- **Registry lookup**: Checks ToolRegistry for tool availability
- **Permission enforcement**: Validates execution rights before invoking
- **Error handling**: Graceful degradation on permission denied or tool not found
- **Disabled tools**: Skips execution for disabled tools

### 3. Conversation Context Management

- **History tracking**: Maintains full message history with assistant and tool results
- **Context clipping**: Implements sliding window strategy to keep within max context tokens
- **System message preservation**: Always retains system prompts
- **Heuristic estimation**: Uses character-based token approximation for efficiency

### 4. Resilience

- **Abort signal support**: Respects caller's AbortController for cancellation
- **Timeout handling**: Propagates timeouts through the execution pipeline
- **Max iterations**: Prevents infinite loops (default 10 iterations)
- **Error events**: Emits errors without crashing the loop

### 5. Protocol Compliance

- **OpenAI-compatible format**: Tool calls conform to `function_calling` spec
- **Stop reasons**: Handles `stop_sequence` (normal end) and `tool_calls` (needs execution)
- **Message roles**: Properly constructs messages with `assistant`, `user`, and `tool` roles

## API Reference

### AgentLoop Constructor

```typescript
constructor(
  engine: AgentEngineAdapter,
  toolRegistry: ToolRegistry,
  config?: AgentLoopConfig
)
```

**Parameters**:
- `engine`: LLM adapter (implements OpenAI-compatible interface)
- `toolRegistry`: Tool registry with all available tools
- `config`: Configuration object

**Config Options**:
```typescript
interface AgentLoopConfig {
  maxIterations?: number;           // Default: 10
  maxContextTokens?: number;        // Default: 128000
  defaultSystemPrompt?: string;
  tokensPerCharacter?: number;      // Default: 0.25 (heuristic)
}
```

### run() Method

```typescript
async *run(request: AgentLoopRequest): AsyncGenerator<AgentLoopEvent>
```

**Request**:
```typescript
interface AgentLoopRequest {
  messages: Message[];
  systemPrompt?: string;
  temperature?: number;
  maxTokens?: number;
  signal?: AbortSignal;
  timeoutMs?: number;
}
```

**Events Emitted**:
- `token`: Individual text token from LLM
- `tool_call`: Tool invocation with name and arguments
- `tool_result`: Outcome of tool execution
- `iteration_complete`: End of one agentic loop iteration
- `complete`: Final completion (success or max iterations reached)
- `error`: Any recoverable or unrecoverable error

### Example Usage

```typescript
import { AgentLoop } from "./server/runtime/loop/agent-loop.ts";
import { OpenAICompatibleClient } from "./server/runtime/loop/openai-compatible.ts";
import { ToolRegistry } from "./src/service/runtime/tools/index.ts";

// Setup
const engine = new OpenAICompatibleClient({
  baseURL: "https://api.openai.com",
  apiKey: process.env.OPENAI_API_KEY,
  model: "gpt-4",
});

const toolRegistry = new ToolRegistry();
// ... register tools ...

const loop = new AgentLoop(engine, toolRegistry);

// Run a conversation turn
const messages = [
  { role: "user", content: "What tools are available?" }
];

for await (const event of loop.run({ messages })) {
  switch (event.type) {
    case "token":
      process.stdout.write((event.data as any).text);
      break;
    case "tool_call":
      console.log(`\nCalling: ${(event.data as any).name}`);
      break;
    case "complete":
      console.log("\n✓ Conversation completed");
      break;
  }
}
```

## Context Clipping Strategy

The loop implements a **sliding window** context management approach:

1. **Calculate total tokens**: Sum all messages using character-based heuristic
2. **If within limit**: Return messages unchanged
3. **If exceeds limit**:
   - Keep ALL system messages (they set agent behavior)
   - Keep most recent non-system messages in reverse order
   - Drop old conversation history from the middle
4. **Result**: Most recent context is preserved, oldest is sacrificed

### Why This Works

- **System prompts are immutable**: Core agent behavior is never lost
- **Recent context is more relevant**: Recent turns are more important than old ones
- **Smooth degradation**: Gracefully shortens history instead of hard failure

## Tool Execution Flow

```
Tool Call Received
      ↓
Check Tool Exists in Registry
      ✗ → Return error "not found"
      ✓
      ↓
Check Tool Not Disabled
      ✗ → Return error "disabled"
      ✓
      ↓
Parse JSON Arguments
      ✗ → Return error "invalid JSON"
      ✓
      ↓
Check Permission
      ✗ → Return error "permission denied"
      ✓
      ↓
Execute Tool.execute(params, context)
      ✗ → Return error with exception message
      ✓
      ↓
Return { success: true, data: result }
      ↓
Emit tool_result event
```

## Integration with M1.1 and M1.4

### M1.1: OpenAI-Compatible Client

The loop receives `AgentEngineAdapter` interface and calls:
- `engine.run(request)` → Returns `AsyncIterable<AgentRunEvent>`
- Handles streaming tokens, tool_calls, and finish signals
- Automatic retry on rate limits and temporary failures

### M1.4: Tool System

The loop consumes `ToolRegistry` for:
- `registry.get(toolName)` → Retrieve tool definition
- `tool.execute(params, context)` → Execute with parameters
- Permission checks via `checkPermission()` function
- Support for disabled tools and all tool sources (builtin, mcp, local)

### Message Protocol

Messages follow the **OpenAI Chat Completion** format:
- `Message.role`: "user" | "assistant" | "system"
- `Message.content`: Text content (optional for assistant with tool_calls)
- `Message.tool_calls`: Array of function calls (assistant only)
- `Message.tool_call_id`: Links tool result back to call (user/tool role)

## Error Handling

| Error | Handling | Result |
|-------|----------|--------|
| Tool not found | Catch in executeTool() | Emit tool_result with error |
| Tool disabled | Check disabled flag | Emit tool_result with error |
| Invalid JSON args | Try-catch JSON.parse() | Emit tool_result with error |
| Permission denied | checkPermission() throws | Emit tool_result with error |
| Tool execution fails | Catch tool.execute() error | Emit tool_result with error |
| Engine error | Catch engine.run() error | Throw and propagate |
| Abort signal | Check signal.aborted | Throw "Request aborted" |

## Performance Considerations

1. **Token estimation**: O(message_count * average_message_length) using heuristic
2. **Tool lookup**: O(1) HashMap get from ToolRegistry
3. **Context clipping**: O(message_count * average_message_length) for token calculation
4. **Memory**: Accumulates full assistant message in memory (potential issue for very long outputs)
5. **Streaming efficiency**: Events are yielded incrementally (doesn't wait for full response)

### Memory Optimization

For very long outputs, consider:
- Streaming directly to storage instead of accumulating
- Chunking large assistant messages
- Implementing circular buffer for history
